OrcaCD is designed to be safe by default, but of course, there are always additional steps you can take to further secure your OrcaCD installation. Here are some best practices to consider:

## Harden OrcaCD

<Checklist id="security-hardening">
	<ChecklistItem id="oidc">
		Use a secure OIDC provider, that enforces strong authentication methods, including secure
		multi-factor authentication (MFA). See the [OIDC guide](/docs/guides/oidc).
	</ChecklistItem>
	<ChecklistItem id="tls">
		Always run the hub behind a secure reverse proxy and ensure that all communication is encrypted
		using TLS.
	</ChecklistItem>
	<ChecklistItem id="trusted-proxies">
		Make sure to configure the `TRUSTED_PROXIES` environment variable correctly to prevent IP
		spoofing attacks. Without it, rate limiting only sees the IP of your reverse proxy.
	</ChecklistItem>
	<ChecklistItem id="allowed-ips">
		Restrict the IPs that can access the hub by configuring the `ALLOWED_IPS` environment variable.
		It does not apply to webhooks, GitHub Actions, the health check and the agent connections.
	</ChecklistItem>
	<ChecklistItem id="agent-allowed-ips">
		Restrict the IPs each Agent can connect from by setting **Allowed IPs** in the settings of the
		Agent.
	</ChecklistItem>
	<ChecklistItem id="restrict-volumes">
		Restrict the volumes that can be mounted to locations within the OrcaCD deployments directory by
		setting the `RESTRICT_VOLUMES_TO_DEPLOYMENTS_DIR` environment variable to `true`. This will
		prevent malicious applications from accessing sensitive files on the host system.
	</ChecklistItem>
	<ChecklistItem id="ips">
		Automatically ban attackers with an Intrusion Prevention System (IPS). The Hub logs failed
		logins, rejected Agent connections and invalid webhook requests as security events. See
		[CrowdSec](/docs/advanced/crowdsec) for an example.
	</ChecklistItem>
	<ChecklistItem id="privileged-apps">
		Keep `ALLOWED_PRIVILEGED_APPS` as short as possible. Applications listed there skip all checks
		of the [deployment policy](#compose-deployment-policy).
	</ChecklistItem>
	<ChecklistItem id="secrets">
		Treat `APP_SECRET` and the agent `AUTH_TOKEN` values like passwords.
	</ChecklistItem>
	<ChecklistItem id="env-files">Give the Agent and the Hub its own env files</ChecklistItem>
	<ChecklistItem id="signed-commits">
		Enable [signed commits](/docs/advanced/architecture/repositories#signed-commits) for
		repositories, so that a compromised Git account can't deploy changes.
	</ChecklistItem>
</Checklist>

All environment variables are described on the [environment variables page](/docs/configuration/env-variables).

## Why is it safe by default?

A big focus of OrcaCD next to ease of use is security. Here are some of the measures we have taken to achieve this:

- All sensitive data is only stored encrypted in the database using the modern [AEGIS-256](https://datatracker.ietf.org/doc/html/rfc10032)
- On top of TLS, every Agent connection uses its own post-quantum-ready handshake and mutual authentication, so a compromised network or proxy can't read or tamper with deployments
- The first admin needs a one-time setup code from the Hub logs and removed users or changed roles take effect immediately
- OrcaCD has a protection layer against [Server-Side Request Forgery (SSRF)](https://developer.mozilla.org/docs/Web/Security/Attacks/SSRF)
- Privileged containers are blocked by default by the [deployment policy](#compose-deployment-policy). Exceptions need an explicit allowlist

## Compose deployment policy

Before every deployment, the Agent checks the Compose file and rejects settings that would give an application access to the host. This way, someone who can push to your repository can't take over the server.

<Accordions>
<Accordion title="What is rejected">

For example:

- `privileged`, `devices` and `volumes_from`
- `cap_add` with host-level capabilities like `SYS_ADMIN`
- Sharing a namespace with the host, e.g. `network_mode: host`
- `security_opt` other than `no-new-privileges`

</Accordion>
<Accordion title="Which host paths can be mounted">

The rules apply to bind mounts, `env_file`, `secrets` and `configs`. Paths must be absolute.

- System paths like `/etc`, `/proc` or the Docker socket are rejected.
- Home directories and credential folders like `.ssh` are rejected.
- Inside the deployments directory, an application can only use its own directory.

With `RESTRICT_VOLUMES_TO_DEPLOYMENTS_DIR=true`, all host paths have to be inside the deployment directory of the application.

</Accordion>
</Accordions>

If an application really needs one of these settings, e.g. a monitoring agent that reads the Docker socket, add its ID to `ALLOWED_PRIVILEGED_APPS` of the Agent. Applications in this list skip **all** checks, so keep it as short as possible.
