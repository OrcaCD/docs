A **Repository** in OrcaCD is a Git repository that contains Docker Compose files. OrcaCD keeps your applications in sync with the repository and uses it as the source of truth for your deployments.

OrcaCD does not clone the repository. It reads branches, the file tree, commits and Compose files through the API of the Git provider.

## Supported Providers

- GitHub
- GitLab (GitLab.com or self-hosted)
- Gitea
- Azure DevOps

<Callout>
	Bitbucket and generic Git repositories are not supported yet. They are shown in the UI but cannot
	be selected.
</Callout>

## Adding a Repository

1. Navigate to the **Repositories** page and click **Add Repository**.
2. **Provider**: Select the Git provider.
3. **Repository**: Enter the repository URL (e.g., `https://github.com/your-org/your-repo`) and optionally an auth token. When you continue, OrcaCD tests the connection to the repository.
4. **Sync type**: Choose a [sync strategy](#sync-strategies) and click **Connect Repository**.
5. **Summary**: For the webhook sync type, OrcaCD shows the webhook URL and secret. Copy the secret, it is only shown once.

![Add Repository dialog](/assets/docs/create-repository.png?url)

OrcaCD stores the URL without a trailing `/` and without a `.git` suffix. Adding a repository whose URL and sync type match an existing repository fails with `409 Conflict`.

## Authentication

If you enter an auth token, OrcaCD uses token authentication. Without a token, the repository is accessed without credentials, which only works for public repositories.

For GitHub, create a [fine-grained personal access token](https://github.com/settings/tokens) with read access to **Contents**.

For GitLab, create a [project access token](https://docs.gitlab.com/ee/user/project/settings/project_access_tokens.html) with `read_repository` scope.

You can change or remove the token later in the **Auth** settings of the repository. Leave the field blank to remove authentication. OrcaCD tests the connection before saving.

## Sync Strategies

The sync type can be changed later in the **Edit Sync** settings of the repository.

![Repository sync settings](/assets/docs/repository-sync-settings.png?url)

### Polling

OrcaCD periodically checks the remote repository for new commits. The default polling interval is **60 seconds**. In the UI, the interval can be set between 60 seconds and 24 hours.

Use polling when:

- You cannot expose an inbound webhook endpoint
- You want a simple setup without additional configuration

### Webhook

OrcaCD listens for push events from your Git provider via webhook. This is more efficient than polling and reacts to new commits instantly. See [Webhooks](/docs/configuration/webhooks#git-providers) for the setup with your Git provider.

To not reveal whether a repository exists, the webhook endpoint returns the same `401` response for unknown repositories, wrong secrets and repositories without the webhook sync type. Webhook requests are rate limited.

### Manual

The repository is only synced when you explicitly trigger a sync from the UI or API.

### What Happens on a Sync

Independent of the sync type, you can always sync a repository manually with **Sync** on the Repositories page or **Sync repository** on the details page of an application.

On every sync, OrcaCD fetches the latest commit of each branch used by the applications of the repository. If the Compose file of an application changed, OrcaCD deploys it. Otherwise, only the new commit is recorded.

## GitHub Actions OIDC

For GitHub repositories, you can enable **GitHub Actions Access** in the sync settings of the repository. This allows GitHub Actions workflows to trigger deployments directly without storing a long-lived token in your CI secrets.

In the same place you can restrict the allowed actions, branches and workflows. See the [GitHub Actions guide](/docs/guides/github-actions) for details.

## Signed Commits

To protect against a compromised Git account, you can require that OrcaCD only deploys commits that are signed by a trusted key. Open the settings of the repository, go to **Signing** and enable **Require signed commits**. Then add the public keys of everyone who is allowed to push deployable commits:

- SSH public keys, one per entry (e.g. `ssh-ed25519 AAAA... user@example.com`)
- Armored GPG public key blocks (`-----BEGIN PGP PUBLIC KEY BLOCK-----`)

At least one key is required, and up to 50 keys are allowed per repository. Keys are configured per repository.

![Signed commits settings](/assets/docs/repository-signing.png?url)

When the setting is enabled, OrcaCD checks the commit before anything is deployed: for polling, webhooks, GitHub Actions, manual syncs and when an application is created or updated. If the commit is not signed by a trusted key, the sync fails, a [notification](/docs/advanced/notifications) is sent and the history of the application records the rejected commit.

How the signature is checked depends on the provider:

- **GitHub and Gitea**: OrcaCD verifies the signature itself.
- **GitLab**: OrcaCD accepts a commit if GitLab reports the signature as verified and the key is on the trusted list. The key also has to be added to the GitLab account of the signer. GPG keys are matched by their key ID.
- **Azure DevOps**: not supported, because its API does not provide signature data.

<Callout>
	The `allowed_signers` format with an email address in front of the key, SSH certificates and X.509
	signatures are not supported. Use plain SSH public keys or GPG keys.
</Callout>

## Deleting a Repository

Deleting a repository also deletes all of its applications. OrcaCD first removes the applications from their Agents, so all affected Agents must be online. If an Agent is offline or fails to remove an application, the deletion stops with an error.

## Repository Status

| Status    | Meaning                            |
| --------- | ---------------------------------- |
| `Success` | Last sync completed without errors |
| `Syncing` | Sync is in progress                |
| `Failed`  | Last sync failed                   |
| `Unknown` | Repository has not been synced yet |
