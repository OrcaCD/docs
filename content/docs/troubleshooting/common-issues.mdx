## Setup code is missing in the Hub logs

**Symptoms:** `docker compose logs hub` does not show a setup code for the first admin account.

**Checks:**

1. The setup code is only printed as long as no user exists. If an account was already created, log in or [recover the account](/docs/troubleshooting/account-recovery).
2. The setup code is logged with the `warn` level. Make sure `LOG_LEVEL` is not set to `error` or `fatal`.
3. A new setup code is generated on every start of the Hub. Always use the code from the latest start.

## Agent stays Offline after connecting

**Symptoms:** The Agent is running but shows as **Offline** in the Hub UI.

**Checks:**

1. Verify `HUB_URL` in the Agent's `agent.env` is correct and reachable from the Agent's host.
2. Confirm the `AUTH_TOKEN` matches the token generated for that Agent in the Hub UI.
3. Check Agent logs: `docker compose logs agent` and look for connection errors.
4. If the Hub is behind a reverse proxy, make sure WebSocket upgrades are forwarded correctly. See the [Reverse Proxy guide](/docs/guides/reverse-proxy).
5. If the logs show `token is missing signing-key segment`, the token was created before v0.4.0. Rotate the token in the Hub UI and update `AUTH_TOKEN`. See [Upgrading](/docs/setup/upgrading).
6. If the Hub uses a self-signed certificate or a certificate from a private CA, mount the CA certificate into the Agent container and set `CA_CERT_FILE` to its path.
7. After changing the `agent.env` file, recreate the container with `docker compose up -d agent`. A plain restart does not reload the env file.

## Agent logs "found the hub's secrets in the agent environment"

The Agent received `APP_SECRET` or `OLD_APP_SECRET`, usually because it shares the `.env` file with the Hub (the default before v0.5.0). The Agent removes these variables at startup, so deployed applications can not read them, but you should give the Agent its own env file:

1. Create an `agent.env` file next to your `docker-compose.yml` and move `HUB_URL`, `AUTH_TOKEN` and all other Agent settings from `.env` into it.
2. Change `env_file: .env` to `env_file: agent.env` in the `agent` service.
3. Recreate the Agent with `docker compose up -d agent`.

## Hub is not accessible / returns 502

**Checks:**

1. Confirm the Hub container is running: `docker compose ps`
2. Check Hub logs: `docker compose logs hub`
3. Verify your reverse proxy is forwarding to the correct port (default: `8080`).
4. If you set `TRUSTED_PROXIES`, confirm the proxy's IP is included. An incorrect value can cause the Hub to reject requests.

## Deployment is stuck in "Syncing"

**Symptoms:** An application stays in the `syncing` state indefinitely.

**Checks:**

1. Verify the Agent is online.
2. Check Agent logs for errors during the Docker Compose up/pull step.
3. Ensure the Agent has access to the Docker API (`use_api_socket: true` in the default `docker-compose.yml`).
4. If the Compose file references private images, run `docker login` for the registry on the Agent host, as the user that starts the Agent, and recreate the Agent with `docker compose up -d agent`. With `use_api_socket`, Docker passes the registry credentials of that user to the Agent. The error `no credentials for <registry> found in the agent's Docker config` means that the Agent has no credentials for this registry.

## Deployment fails with permission denied during symlink checks

**Symptoms:** A deployment or redeployment fails with `could not be checked for symlinks` and `permission denied`, for example when a bind mount source is `/deployments/my-app/data/app`.

Application containers can create directories owned by their own UID or GID with restrictive permissions, such as `0700` or `0750`. The Agent must be able to search every parent directory to inspect the mount source. The default Agent configuration drops all Linux capabilities, so running as root alone does not bypass these permissions.

The symlink checks prevent an application from creating a symlink in a writable bind mount and using it as a mount source on a later deployment to access paths outside its own directory. A path that cannot be inspected is rejected.

**Solutions:**

1. Prefer adjusting ownership, group membership or an ACL on the affected parent directories so the Agent can search them. Check every parent of the path named in the error and account for the UID and GID used by the application container. Avoid making application data world-readable or world-writable.
2. If those permissions cannot be changed, explicitly add `DAC_READ_SEARCH` to the **Agent service's** Compose configuration. Merge this into the existing service, keeping its other settings:

   ```yaml
   services:
     agent:
       cap_drop:
         - ALL
       cap_add:
         - DAC_READ_SEARCH
   ```

3. After changing the Agent's Compose configuration, recreate it with `docker compose up -d --force-recreate agent`, then retry the deployment. A plain restart does not apply capability changes.

<Callout type="warn">
	`DAC_READ_SEARCH` bypasses file read and directory read/search permissions for **all files
	accessible to the Agent**, not just the deployments directory. It does not bypass write
	permissions. This capability is disabled by default; enable it only if you accept that broader
	read access. Symlink checks remain enabled.
</Callout>

Adding the application to `ALLOWED_PRIVILEGED_APPS` skips all deployment security policy checks. Prefer fixing directory access or explicitly granting the capability instead of bypassing the policy for this error.

## Repository sync fails with authentication error

**Symptoms:** Sync status shows `failed` with an authentication error.

**Checks:**

1. Confirm the auth token is still valid and has not expired or been revoked.
2. For token auth, verify the token has `read_repository` (GitLab) or `Contents: read` (GitHub) permissions.
3. Update the token in the repository settings under **Authentication**. OrcaCD tests the connection before saving and shows an error if the credentials are invalid.

## Webhook sync not triggering

**Symptoms:** Pushes to the repository do not trigger a sync.

**Checks:**

1. Confirm the webhook URL and secret in your Git provider match what OrcaCD shows in the repository settings. OrcaCD responds with `401` for unknown repositories, wrong secrets and repositories whose sync type is not **Webhook**. See [Webhooks](/docs/configuration/webhooks#responses-and-rate-limits).
2. Check that the Hub is publicly reachable on the configured `APP_URL`.
3. Review the webhook delivery logs in your Git provider (GitHub: Settings → Webhooks → Recent Deliveries) to see if the request reached the Hub.
4. Verify the webhook is configured to send **push** events.

## Cannot log in after enabling OIDC / disabling local auth

If you locked yourself out by disabling local authentication, see [Account Recovery](/docs/troubleshooting/account-recovery).
